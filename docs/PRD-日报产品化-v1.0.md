## 二、背景与目标

### 2.1 背景

引擎 v2.5.0 已具备完整能力：取证脚本生成证据骨架 → 证据门校验 → agent 用 NeoData MCP 补证 → 报告门校验 → 渲染手机优先的 HTML → 写入 `<meta name="daily-gate">` 签名。83 项回归测试全绿，`doctor` 全绿。

但它现在是**开发者自用的手动流程**，不是产品。产品化缺口有五处（2026-10-22 实测盘点）：

| 编号 | 断点 | 证据 | 用户感受 |
|---|---|---|---|
| B1 | 手机侧交付为 0 | `config/delivery.json` 为 `enabled:false`、`to:""` | 报告只落在电脑里 |
| B2 | 原定邮件通道物理不通 | Agent 邮箱 `not_bound` | 填了收件人也发不出（已由 D-02 移出范围） |
| B3 | 无人值守从未端到端验证 | 中间「填 data.json」只能在对话内完成 | 定时任务可能空转且不报错 |
| B4 | 失败完全静默 | 退出码 10/11/12 无人主动查看则无人知晓 | 挂了要自己发现 |
| B5 | 文档数字漂移 | README 写「8 脚本 / 62 测试 / v2.4.0」，实际 11 / 83 / 2.5.0 | 换电脑重建会踩坑 |

### 2.2 要解决的问题

一句话：**让每天的产出，在我不碰电脑的情况下，落到我手机上；产出有缺口时如实说明；产出失败时我能第一时间知道。**

### 2.3 目标与成功指标

| 编号 | 目标 | 指标与口径 | 目标值 |
|---|---|---|---|
| G1 | 三时段报告在手机可读 | **交付及时率** = 报告在时段开始后 15 分钟内可打开的次数 ÷ 应出报告次数（周一至周五，法定节假日顺延） | ≥ 95% |
| G2 | 无需人工干预 | **无人干预率** = 无人介入完成全链的批次 ÷ 总批次 | 连续 10 个交易日 100% |
| G3 | 失败可知 | **告警到达时延** = 从批次失败到 Bark 通知送达的时长 | ≤ 30 分钟（目标 ≤ 5 分钟） |
| G4 | 缺口如实披露 | **缺口披露率** = 含非空缺口清单的降级报告数 ÷ 降级报告数 | 100% |
| G5 | 数据源可扩展 | **新数据源接入成本** = 接入 1 个新 MCP 数据源所需人日 | ≤ 0.5 人日，且不改动主流程脚本 |

> 口径说明：G1 分母按交易日机械计算，不含节假日；「可打开」以 App 内实际渲染成功为准，不以「已上传」为准。

### 2.4 硬性约束

- C-01 定时任务运行本机（Windows），**电脑关机则当日不产出**，不承诺 7×24。
- C-02 不得造假、不得占位。数据缺失只有一种表达：写进缺口并降级标注。
- C-03 门禁的强制力必须仍在脚本退出码上，不能退化为「靠模型自觉」。
- C-04 报告与证据含真实持仓与金额，**不得出现在任何公开可访问 URL**。
- C-05 沿用既有视觉约定：始终深色、涨红跌绿（A 股习惯）、结论优先、细节折叠。

## 三、名词与术语

| 术语 | 定义 |
|---|---|
| 批次（Run） | 一个时段内的一次完整执行：取证 → 补证 → 门禁 → 渲染 → 发布 → 通知 |
| 时段（Session） | `pre`（08:30 盘前）、`noon`（12:00 午间）、`post`（20:00 盘后） |
| 骨架（Skeleton） | `fetch_data.py` 生成的证据 JSON 空壳，字段齐全、值为 `missing` |
| 补证（Enrichment） | agent 通过 MCP 或搜索把值填进同一份证据 JSON |
| 门禁（Gate） | 证据门 `gate_check` 与报告门 `render_report` 的双重机械校验 |
| 降级版（Degraded Report） | 门禁未 PASS 但仍输出的报告，签名标记为 `DEGRADED` |
| 缺口（Gap） | 字段级缺失记录，含字段名、原因、影响、可用替代源 |
| 通道（Channel） | 送达路径：**阅读通道**（App 内打开 HTML）、**通知通道**（Bark） |
| 适配器（Adapter） | 把某个数据源（MCP/API/SDK）的返回映射到标准字段的函数 |
| 覆盖度（Coverage） | 已取到真实值的字段数 ÷ 该市场该时段应有字段数，由脚本机械计算 |

## 五、方案对比与选型

### 5.1 核心决策点：手机如何读到全文

| 方案 | 实现方式 | 实现成本 | 手机可读性 | 数据私密性 | 稳定性 | 结论 |
|---|---|---|---|---|---|---|
| A1 邮件附件 | 定时任务发 HTML 附件 | 低 | 中（附件需下载再打开） | 中（邮件明文在第三方服务器） | 高 | **否决**（D-02） |
| **A2 私有空间 + App 阅读 + Bark 深链** | 报告上传至账号私有空间（Library），Bark 推送摘要与链接，点击跳 App 内打开 | 中 | **好**（原生渲染 HTML） | **中高**（账号私有，非公开） | 高 | **推荐** |
| A3 本地 HTTP 服务 + 内网穿透 | 本机起服务，公网域名访问 | 中 | 好 | **低**（链接泄露即暴露持仓） | 低（穿透易断、IP 变动） | 不选 |
| A4 每次发布为独立站点 | 每天部署新站点 | 中 | 好 | 中（若为公开链接则低） | 中（链接变更、部署失败点增加） | 备选 |

**推荐 A2 的理由**：
1. 阅读体验最好——HTML 在 App 内原生渲染，锚点目录、折叠卡片、深色主题全部可用，而不是像 Bark 正文那样被截断。
2. 私密性可接受——载体是账号私有空间，不是公开站点，符合 C-04。
3. 与 D-01 完全一致——Bark 只承担「叫醒」，不承担「承载」。

**A4 作为备选触发条件**：若 A2 的载体验证不通过（例如无法在 App 内直接渲染 HTML），则退到 A4；仍不通则退到「Bark 正文推送纯文本摘要版」（可读但无卡片与折叠）。

> **验证结论（2026-10-22，RK-01 关闭）**：App 内可直接渲染报告 HTML，A2 成立，A4 备选不需要启用。
> 实现上比原设计更轻：**不必先上传 Library** —— 桌面侧 `present_files` 产出的 HTML 在 App 任务详情里
> 就是原生渲染的产物卡片，Bark 通知只负责把人叫过来。因此 FR-01 的「取回可点击链接」降为**可选**
> （`config/notify.json` 的 `read_url_base` 留空即可），少一个上传失败点，也少一次数据出本机。

### 5.2 第二决策点：数据不全怎么办

| 方案 | 做法 | 问题 | 结论 |
|---|---|---|---|
| B1 现状：门禁 FAIL 即删报告、退出码 12 | 宁可不发 | 用户当天完全拿不到信息，最差体验 | 否决（D-03） |
| B2 全面放开：门禁只警告 | 照发 | 门禁形同虚设，造假无人拦 | 否决（违反 C-03） |
| **B3 降级发布：门禁 FAIL → 头部横幅 + 缺口清单 + DEGRADED 签名** | 数据真伪仍被拦，但信息照常送达 | 需新增渲染分支 | **推荐** |

**B3 的关键设计**：门禁仍然会 FAIL、仍然会给出退出码（可被监控），但**不再删除报告**，而是产出一份「真实但残缺」的降级版。区分标准写死为：
- **阻断级**（Blocking）：标的无现价、证据 ID 悬空、多空同源。这类不得进入论点，论点必须改写或撤下。
- **降级级**（Degraded）：新闻不足条数、产业链笔记缺失、覆盖率低于阈值。可发，但横幅标注。
- **提示级**（Info）：非关键字段缺失（如基金规模变动、北向资金）。只在缺口区列表，不影响横幅。

### 5.3 第三决策点：数据源如何扩展（D-03 后半句）

| 方案 | 做法 | 问题 | 结论 |
|---|---|---|---|
| C1 每接一个源改主流程 | 在 `fetch_data.py` 里加 if 分支 | 越加越乱，回归风险高 | 否决 |
| **C2 注册表 + 适配器** | `config/data-sources.json` 声明 字段→源优先级；每个源一个 `adapter_<name>.py`，实现统一接口 `fetch(field, ctx) -> (value, source_note) \| None` | 需先定接口契约 | **推荐** |

## 七、功能需求

> 优先级：Must（本期必做）/ Should（本期应做）/ Could（可选）。验收标准用 Given/When/Then。

### M1 发布与送达

#### FR-01 报告上传至阅读载体（Must）

**描述**：批次渲染成功（无论 PASS 或 DEGRADED）后，把 HTML 上传到账号私有空间，取回可访问链接，写入批次清单。

**验收**：
- Given 报告已生成且非空，When 执行发布，Then 返回一个 URL 并记录到 `data/daily-reports/run-log.csv` 的 `read_url` 列。
- Given 上传失败（网络/权限/容量），When 重试 2 次仍失败，Then 标记 `publish_status=FAILED`，跳过通知并触发 FR-11 告警。
- Given 同一时段重复执行，When 再次发布，Then 覆盖同一份报告（同名文件），不产生重复条目。

#### FR-02 报告命名与可检索（Must）

**描述**：上传文件命名规则固定为 `持仓日报_YYYY-MM-DD_时段.html`，保证在载体列表中按日期可辨。

**验收**：
- Given 时段为 `pre`、日期为 2026-10-22，When 上传，Then 载体中显示名为 `持仓日报_2026-10-22_盘前.html`。
- Given 用户在某载体列表中翻找，When 按日期排序，Then 同日三份报告顺序为 盘前 → 午间 → 盘后。

#### FR-03 Bark 通知推送（Must）

**描述**：发布成功后推送一条 Bark 通知，字段映射如下：

| Bark 字段 | 内容 | 约束 |
|---|---|---|
| `title` | `持仓日报 · 盘前` / `午间` / `盘后` | ≤ 20 字 |
| `subtitle` | 市场天气 + 覆盖率，如 `A股偏弱 · 覆盖 78%` | ≤ 30 字 |
| `body` | 3–5 行摘要：今日动作 / 到价提醒 / 缺口提示 | ≤ 400 字，超出截断并追加「详情点开看」 |
| `url` | 阅读载体链接（App 内打开） | 必须为 FR-01 返回的 URL |
| `group` | `持仓日报` | 固定，便于在 Bark 内聚合 |
| `level` | 盘前/盘后 `active`；午间 `passive` | 避免午间强打扰 |
| `sound` | 盘前 `bell`，午间 `none`，盘后 `bell` | — |

**验收**：
- Given 报告发布成功，When 推送，Then 手机 60 秒内收到通知，标题包含时段名。
- Given 报告为降级版，When 推送，Then `subtitle` 以「⚠ 数据不全」开头，`body` 第 1 行说明缺什么。
- Given Bark Key 无效或服务不可用，When 推送失败，Then 记录 `notify_status=FAILED`，不重试超过 2 次，不影响报告本身可用。

#### FR-04 通知内容分级摘要（Must）

**描述**：三个时段的摘要内容不同，不能一份模板套三次。

| 时段 | 摘要必含 | 摘要禁止含 |
|---|---|---|
| 盘前 | 今日动作（加/减/观察）+ 到价标的 + 隔夜关键消息 1 条 | 长篇技术分析 |
| 午间 | 半日异动 + 是否需盘中处理 | 重复盘前结论 |
| 盘后 | 今日复盘一句 + 明日关注 + 关注库到价清单 | 逐条复述持仓 |

**验收**：
- Given 生成盘前摘要，When 检查内容，Then 包含「今日动作」关键词且不含任何技术指标名（如 MACD/KDJ）。
- Given 三时段摘要，When 两两比对，Then 文字重复率 < 40%。

#### FR-05 通知静默与免打扰（Should）

**描述**：非交易日、非交易时段不推送；单日推送上限 3 条（不含告警）；连续失败告警不受静默限制。

**验收**：
- Given 当日为周六，When 定时任务被触发，Then 不发布不推送，记录 `skipped=non_trading_day`。
- Given 同一天已推送 3 条正常报告，When 第 4 次触发，Then 不再推送正常通知，但告警仍可发。

### M2 门禁降级（本期语义变更核心）

#### FR-06 门禁 PASS 路径保持原样（Must）

**描述**：双门 PASS 时行为与 v2.5.0 一致：写签名 `<meta name="daily-gate" content="PASS ...">`，正常发布。

**验收**：
- Given 证据齐全且报告门通过，When 渲染完成，Then HTML 含 `PASS` 签名，且报告的覆盖率横幅数值与脚本机械计算值完全一致。

#### FR-07 门禁 FAIL 改为降级发布（Must，语义变更）

**描述**：证据门或报告门 FAIL 时，**不再删除 HTML**，改为：
1. 在报告最顶部插入降级横幅（红底、不可折叠、占满宽度）；
2. 签名写为 `<meta name="daily-gate" content="DEGRADED ...">`，并附失败原因列表；
3. 进程退出码**仍返回非 0**（`10`/`11`/`12`），供监控判定；
4. 缺口清单区默认展开。

**验收**：
- Given 某标的新闻仅 1 条（要求 ≥2），When 走报告门，Then 报告仍生成，顶部有「数据不全」横幅，签名含 `DEGRADED` 与 `news_insufficient`，退出码为 `12`。
- Given 门禁 FAIL 但报告已发布，When 用户在 App 打开，Then 横幅在首屏可见，无需展开即可读到「缺什么」。
- Given 阻断级问题（无现价/证据 ID 悬空），When 渲染，Then 该标的**不出论点卡**，只在缺口区列出「因证据不足未出结论」，不得出现「基于推测」类表述。

#### FR-08 缺口三级分类与渲染（Must）

**描述**：所有缺口按 5.2 定义分为阻断/降级/提示，分别渲染：

| 级别 | 渲染位置 | 样式 | 是否影响横幅 |
|---|---|---|---|
| 阻断 Blocking | 缺口区首段 + 对应卡片占位条 | 红边 | 是 |
| 降级 Degraded | 缺口区中段 | 琥珀边 | 是 |
| 提示 Info | 缺口区折叠段 | 灰边 | 否 |

**验收**：
- Given 缺口为提示级（如基金规模变动缺失），When 渲染，Then 顶部横幅不出现，仅缺口折叠区内列出。
- Given 缺口为阻断级，When 渲染，Then 横幅列出该标的名称与缺失字段名，用户可不展开即知。

#### FR-09 降级原因徽标（Must）

**描述**：每张卡片右上角显示一个小徽标，标明该卡数据是否完整：`完整` / `部分缺失` / `证据不足`。徽标颜色与 FR-08 级别对应。

**验收**：
- Given 某卡片 5 个字段缺 1 个，When 渲染，Then 卡片显示「部分缺失」徽标，长按/悬停显示缺失字段名。
- Given 卡片数据完整，When 渲染，Then 显示「完整」徽标（不隐藏，便于快速扫视哪些卡可信）。

#### FR-10 降级累计与趋势提示（Should）

**描述**：报告顶部摘要条显示「近 5 个交易日降级 3 次」。连续 3 次降级时，横幅追加一行「数据源可能已失效，建议检查」。

**验收**：
- Given 近 5 日有 3 次降级，When 渲染，Then 摘要条出现该计数。
- Given 连续 3 次降级，When 渲染，Then 横幅含「建议检查数据源」提示，并在告警中附带该信息。

### M3 告警

#### FR-11 批次失败告警（Must）

**描述**：以下任一情形触发 Bark 告警（`level=timeSensitive`，`sound=alarm`）：
- 取数全失败（所有标的 `missing`）
- 发布失败
- 脚本异常退出（非 0/10/11/12 的退出码）
- 批次超时（超过 NFR-01 时限的 2 倍）

**验收**：
- Given 取数全失败，When 批次结束，Then 5 分钟内收到告警，正文含「哪一步、哪个时段、错误摘要一行」。
- Given 告警已发，When 用户点击通知，Then 跳到该批次的日志摘要页（或 App 内错误说明页）。

#### FR-12 每日心跳（Could）

**描述**：每个交易日最后一次批次（盘后）成功后，若当日有降级，则在通知正文末尾追加一行「今日 1 次降级，已标注」。全正常则不追加。

**验收**：
- Given 当日 3 个批次全部 PASS，When 盘后通知发出，Then 正文不含降级提示。
- Given 当日有 1 次降级，When 盘后通知发出，Then 正文含「今日 1 次降级」。

### M4 数据源可插拔

#### FR-13 数据源注册表（Must）

**描述**：新增 `config/data-sources.json`，结构如下（示例，非最终格式）：

```json
{
  "sources": {
    "akshare":  { "enabled": true,  "kind": "sdk", "adapter": "adapter_akshare.py",  "timeout_s": 60 },
    "neodata":  { "enabled": true,  "kind": "mcp", "adapter": "adapter_neodata.py",  "timeout_s": 120 },
    "tushare":  { "enabled": false, "kind": "sdk", "adapter": "adapter_tushare.py",  "timeout_s": 60 }
  },
  "field_priority": {
    "close":        ["akshare", "neodata"],
    "pe_ttm":       ["neodata"],
    "north_flow":   ["tushare", "neodata"],
    "fund_scale":   ["neodata", "akshare"]
  }
}
```

**验收**：
- Given 某字段的优先级链中第一个源返回有效值，When 取数，Then 不再调用后续源，并记录 `source=第一个源`。
- Given 某字段未在 `field_priority` 中声明，When 取数，Then 使用默认链（当前启用的所有源按注册顺序），并在日志中标注 `priority=default`。
- Given 注册表 JSON 语法错误，When 启动批次，Then 立即失败并告警，不静默使用旧值。

#### FR-14 适配器统一接口（Must）

**描述**：每个数据源一个适配器模块，必须实现：

```
fetch(field: str, ctx: dict) -> tuple[value, source_note] | None
```

- 返回 `None` 表示该源无此字段（不是失败）；
- 抛异常表示该源本次不可用，触发链上下一个源；
- `source_note` 记录原始单位与口径，供报告脚注引用。

**验收**：
- Given 新增 `adapter_tushare.py` 并在注册表启用，When 次日运行，Then 无需改动 `fetch_data.py` 即可取到 `north_flow`。
- Given 适配器内部抛异常，When 取数，Then 自动切下一个源，缺口里记录「tushare: 超时」，不中断整批。

#### FR-15 字段级覆盖度报表（Must）

**描述**：每批次额外产出 `data/daily-reports/coverage/YYYY-MM-DD.json`，逐字段记录：是否取到、来自哪个源、尝试过哪些源、耗时。

**验收**：
- Given 批次完成，When 检查覆盖度文件，Then 每个应有字段都有一行，包含 `field / got / source / tried / cost_ms`。
- Given 某字段连续 5 日未取到，When 查看报表，Then 能一眼看出（标记 `stale_5d: true`），作为接新源的依据。

#### FR-16 新源接入文档与自检（Should）

**描述**：`references/data-source-adapter.md` 给出 30 行以内的最小接入模板；`derive_indicators.py --selftest` 扩展为 `python scripts/adapter_selftest.py <name>`，用固定样本验证适配器映射正确。

**验收**：
- Given 按文档接入新源，When 运行自检，Then 输出「3 个字段映射正确 / 1 个单位不符」类结论，而不是只报「通过」。

### M5 运维与文档

#### FR-17 README 数字自动校准（Should）

**描述**：README 中的「脚本数 / 测试数 / 当前版本」三个数字由 `release.py doctor` 校验；不一致时 `doctor` 返回非 0 并指出具体行。

**验收**：
- Given README 写「62 项测试」而实际为 83，When 运行 `doctor`，Then 退出码非 0，输出指出 README 第 N 行数字与实测不符。
- Given 发版执行 `bump`，When 完成，Then README 中版本号同步更新，无需手改。

#### FR-18 换机重建与备份（Should）

**描述**：`scripts/backup.py` 打包 `config/` 与 `data/`（不含 `.git`），产出带日期的加密 zip；`scripts/setup_local.py` 增加 `--restore <zip>` 从备份恢复。

**验收**：
- Given 执行备份，When 检查产物，Then zip 内含 holdings/watchlist/delivery/data-sources 四个配置与最近 30 天报告。
- Given 在新机器 clone 代码后恢复备份，When 运行 `doctor`，Then 全绿且能立即出报告。

## 九、业务流程与状态流转

### 9.1 主流程

```
交易日 08:30 / 12:00 / 20:00
        │
        ▼
   [1] 交易日判定 ──否──> 记录 skipped，结束
        │是
        ▼
   [2] 取证 fetch_data.py ──失败──> [A] 全 missing 骨架
        │成功                                    │
        ▼                                        │
   [3] 补证（agent + MCP 适配器链）<──────────────┘
        │
        ▼
   [4] 派生指标 derive_indicators.py
        │
        ▼
   [5] 证据门 gate_check ──FAIL──> 记录失败原因（不终止）
        │PASS/FAIL 均继续
        ▼
   [6] 分析并填 data.json（agent）
        │
        ▼
   [7] 渲染 render_report.py ──阻断级──> 卡片不出结论，仅缺口占位
        │
        ▼
   [8] 写签名 PASS / DEGRADED
        │
        ▼
   [9] 发布（FR-01）──失败──> [B] 告警，结束
        │成功
        ▼
  [10] 通知 Bark（FR-03/FR-04）
        │
        ▼
  [11] 写批次清单 + 覆盖度报表
```

### 9.2 批次状态机

| 状态 | 触发事件 | 迁移到 | 允许操作 |
|---|---|---|---|
| `PENDING` | 定时任务触发 | `TRADING_DAY_CHECK` | 取消 |
| `TRADING_DAY_CHECK` | 非交易日 | `SKIPPED`（终态） | — |
| `TRADING_DAY_CHECK` | 交易日 | `FETCHING` | 取消 |
| `FETCHING` | 取数完成（含全 missing） | `ENRICHING` | 重跑（覆盖） |
| `FETCHING` | 脚本异常 | `FAILED` | 重跑 |
| `ENRICHING` | 补证完成 | `GATING` | 追加补证（幂等覆盖） |
| `ENRICHING` | 超时 | `DEGRADED` | 强制进入 GATING |
| `GATING` | 双门 PASS | `RENDERING` | — |
| `GATING` | 任一门 FAIL | `RENDERING`（标记 DEGRADED） | — |
| `RENDERING` | 渲染成功 | `PUBLISHING` | 重渲染 |
| `RENDERING` | 阻断级且全部标的无结论 | `FAILED` | 重跑 |
| `PUBLISHING` | 上传成功 | `NOTIFYING` | 重发布（同文件覆盖） |
| `PUBLISHING` | 上传失败 | `FAILED` | 重试 ≤2 次 |
| `NOTIFYING` | 推送成功 | `DELIVERED`（终态） | — |
| `NOTIFYING` | 推送失败 | `DELIVERED_NO_NOTICE`（终态） | 补发 |

> **状态单向流转**：`DELIVERED` 后不得回退；重跑生成新 `run_id`，不复用旧记录。

### 9.3 报告状态

`DRAFT`（渲染完成未签名）→ `SIGNED_PASS` 或 `SIGNED_DEGRADED` → `PUBLISHED` → `ARCHIVED`（超过 90 天移入归档目录，不删除）

## 十、数据与埋点

### 10.1 批次清单 `data/daily-reports/run-log.csv`

| 字段 | 类型 | 说明 |
|---|---|---|
| `run_id` | string | `YYYYMMDD-<session>-<seq>` |
| `session` | enum | pre / noon / post |
| `started_at` / `ended_at` | ISO8601 | 含时区 |
| `duration_s` | int | 端到端耗时 |
| `status` | enum | 见 9.2 终态集合 |
| `gate_result` | enum | PASS / DEGRADED |
| `coverage_pct` | float | 机械计算值（不可手填） |
| `gaps_blocking` / `gaps_degraded` / `gaps_info` | int | 三级缺口计数 |
| `read_url` | string | 阅读载体链接 |
| `notify_status` | enum | SENT / FAILED / SKIPPED |
| `degraded_streak` | int | 截至当日的连续降级次数 |

### 10.2 覆盖度报表 `data/daily-reports/coverage/YYYY-MM-DD.json`

字段级：`field / got(bool) / source / tried[] / cost_ms / stale_5d`

### 10.3 关键指标口径

| 指标 | 计算式 | 排除项 |
|---|---|---|
| 交付及时率 | 发布成功且 `duration_s ≤ 900` 的批次数 ÷ 应出批次数 | 非交易日、用户主动跳过 |
| 无人干预率 | 无人工补证/重跑的批次数 ÷ 总批次数 | 节假日 |
| 缺口披露率 | 含非空 gaps 的 DEGRADED 报告数 ÷ DEGRADED 报告总数 | — |
| 平均覆盖率 | 各批次 `coverage_pct` 算术平均 | 降级批次计入，不剔除 |

### 10.4 埋点（本地事件，不上报）

事件：`batch_start` / `fetch_done` / `enrich_done` / `gate_result` / `render_done` / `publish_result` / `notify_result`。每条含 `run_id` 与 `session`，写同一日志文件，供事后排查。
